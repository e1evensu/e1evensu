# 单题成功不是能力

做 Agent 评测最容易犯的错，是把"这次跑通了"当成"它具备这个能力"。

前者是一个事件，后者是一个统计声明。

## 五个不能外推的东西

**厂商报告不能当基线。**
各家发布页上的分数，条件通常不公开：什么 harness、多少预算、几次尝试取最好、有没有针对题目调过提示。拿它跟自己跑到一半的结果比，比出来的不是差距，是两套不同实验的差值。真正可比的只有：同一个模型、同一套冻结的 harness、同一个评分器、同一批任务。

**子集成绩不能外推全集。**
33 道题跑出 60%，不代表 66 道题也是 60%。题目难度的分布不是均匀的，你选的子集往往受资源限制——CPU、内存、显存、墙钟时间。这些约束筛掉的可能正是最难的那部分。子集成绩只能说明"在这个子集上"，一个字的引申都是编。

**单次成功不能当能力。**
一次通过可能是运气、可能是题目恰好落在模型的舒适区。能力要看分布：同一批任务跑多次，通过率的区间在哪，方差多大。5 次里过 3 次和 5 次里过 1 次，是两种完全不同的东西，但都叫"跑通了"。

**模型自评不算证据。**
让模型自己判断"我做完了吗"，得到的是它的信心，不是它的正确率。这两者在模型身上相关性很弱——越是在错误前提上推理，它越自信。

**机制调用量不能当进展。**
"新增了 3 个工具"、"委派了 4 个子会话"、"调用链达到 7 层"，这些是过程指标。过程指标能诊断问题，但不能证明能力。一个 Agent 调用了很多工具却什么也没交付，和一个 Agent 只用了两个工具就交付了可验证的结果，后者更强。

## 那什么算证据

只剩一条：**在没参与过调参的任务上，完成率提升了，成本和退化可接受。**

这句话每个限定词都在挡东西：

- "没参与过调参" — 挡掉过拟合。在调过的题上涨分说明不了任何事
- "完成率" — 挡掉单点运气。要看一批任务的整体分布
- "提升" — 挡掉绝对值。没有基线的数字没有意义
- "成本和退化可接受" — 挡掉用 10 倍预算换 1% 涨分

四道关卡全过，才算一个能力声明。

## 衡量标准会塑造系统

认可"这次跑通了"，所有人就会去优化"这次跑通"——挑软题、加预算、改提示直到这次过。每一轮都有明显进展，每一轮的单题演示都好看，换个任务就崩。

只认可分布上的提升，唯一能走的路就是让系统普遍变强。这条路慢。
