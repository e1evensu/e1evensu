# 自证陷阱：292 项检查全过，官方 4 项失败

一次长任务评测里，模型交出了产物，同时附上一份自己写的验收清单——292 项检查，全部通过，报告零失败。

同一个产物送进官方评分器：20 项，4 项失败。

其中一项是工单时长。题面要求"routing duration 包含 setup 时间"，模型判断这张 WIP 工单不需要重新 setup，于是按不含 setup 计时。它自己那 292 项检查里，这一项也是按不含 setup 算的——当然通过。

算术没错。问题在别处：**检查和产物共用了一套假设**。

## 检查项越多，错误越像真的

模型写验收清单的方式，是把"我理解的题面"翻译成断言，然后拿这套断言去验证"我按这个理解做出的产物"。

这不是验证，是一次带回溯的复述。

292 项检查不代表 292 次独立确认，而是同一个前提被复述了 292 遍。项数带来的不是可靠性，是可信的外观——而且这个外观对写检查的模型自己也生效。它看到 292 个绿勾，就真的相信自己做对了。

更麻烦的是这个过程的自我强化：检查写得越细，看起来越严谨；看起来越严谨，越没有人（包括模型自己）去怀疑那个被复述了 292 遍的前提。

## 四种"完成"被混成了一种

做这类系统时我坚持把四件事分开记：

- **执行成功** — 进程退出码是 0
- **结果被接受** — 有人认领了这份产物
- **依据支持** — 有原始材料能支撑它
- **验证通过** — 独立检查过

置信度从低到高，差得很远。执行成功只说明没崩，不说明做对。结果被接受只说明有人签收，不说明可复现。

现实中最常见的错误，是把最低那档当成最高那档：跑完了、有日志、有输出，就宣布完成。日志证明的是"跑过"，不是"对"。

把四件事压成一个 `done`，等于把整条验证链烧掉，只留一个状态位。

## 让验证真的能推翻结论

三件事，按代价从低到高：

**一、从原始要求重新推导断言，不要从实现假设推导。**
写检查的时候，眼不见实现。只看题面，重新问"这里到底要求什么"。上面那个例子里，如果回到题面原文——"use routing durations with setup"——WIP 要不要 setup 就不需要判断了，题面说了算。判断一旦发生，就说明在解释题面，而解释是可以错的。

**二、验证方不看实现过程。**
独立上下文、独立会话、只有题面和产物。看过实现过程的验证者，会被实现的逻辑说服——这是人的问题，也是模型的问题。独立不是形式，是让"不知道作者怎么想的"成为一种能力。

**三、允许"未验证"是一个合法状态。**
比"误判为通过"更危险的是没有这个状态。系统里如果只有 pass / fail 两档，所有不确定的东西都会被挤进 pass。必须有第三档：我检查了，但没能力确认。留下这个洞，比填上一个假结论好。

## 最后

"可核验"不是"有证据"。有证据太容易了——任何一次执行都能留下日志、trace、截图。

可核验是：证据有能力推翻结论，而结论确实经过了这次推翻的检验。

前者是记录，后者是验证。大部分号称可核验的系统，只做到了前者。
